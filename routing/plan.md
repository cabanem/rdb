The Developer API is plain REST with a bearer token, `UrlFetchApp` posts binary payloads (the RLCM import is a blob with `application/octet-stream`), it follows the package-download redirect by default, and the polling loops fit inside an execution with `Utilities.sleep`. The control flow we wrote out — find-or-create, reverse order on stop, "missing in either direction is fatal" — is plainly easier to read as forty lines of JavaScript than as fifteen recipe steps, and POOL-14's core is already a code step. It would live in your repo under version control, next to lib_sdc, with the registry Sheet as the only state store: no `RTR_Pool`, no `RTR_PoolJobs`, no `/status` polling across a boundary, because the workbook would be orchestrator and UI at once.

I'd still keep it in Workato, for two reasons that I think are decisive and one that's a matter of taste.

**Secrets custody.** The orchestrator has to hold a Developer API token for every client workspace, the golden token, and the service account's private key. In Workato those sit in a data table behind the workspace's access controls and, for the SA key, encrypted in a connection. In Apps Script they'd sit in Script Properties or a Sheet tab — readable by anyone who can edit the routing workbook, which is ops, by design. Secret Manager is reachable from Apps Script, but then you're building a second secrets path to avoid the first. Workato-admin credentials living on the Google side also cuts against the scoping you set: Google resources for the analyst-facing bits only.

**Execution model.** A prepare is a five-to-ten-minute job with two async waits, a quota-paced loop, and a human pause in the middle. Apps Script gives you a per-execution limit and time-driven triggers, so you'd rebuild the state machine anyway — job rows, resume-from-cursor, retry — and get less back: no per-step job history, no error monitor, no rerun button. That's the part Workato's long actions and job model provide for free, and it's most of what the orchestrator design is.

**Boundary, as taste.** Workato-about-Workato stays inside Workato: the thing that provisions a workspace is itself a Workato asset, promotable with RLCM, and the connector is already shared with your DEV→TEST→PROD pipeline. The workbook stays what it is today — registry, claim, and the analyst surface.

One thing worth noticing: the decision is cheap to reverse. `/prepare`, `/status`, `/register` are the boundary, and `Registry` in lib_sdc is the seam. If the calculus changes — a proper secret store reachable from GAS, or Workato turning out to be a worse place to iterate than the editor fixes in §2 suggest — the workbook wouldn't know the implementation moved. That's the real payoff of having written the OpenAPI spec before either side exists.

Where I *would* have gone the other way: if the pool were touched a few times a year by one person, with no per-workspace secrets because an org-level Developer API credential existed. Then a single script with one token beats seven recipes and three tables.
